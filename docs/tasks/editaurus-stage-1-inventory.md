## Intent, acceptance criteria and evidence rules

Connect the application's current editaurus contract, its interactive catalog and
the portable `/Users/lukkul/Projects/editaurus-ui/SKILL.md`. Assess the user's new
architectural decision: shadcn/ui is the component foundation, Base UI is the
compatible interaction implementation, and editaurus specifies appearance,
variants, states and usage. Preserve accepted appearance and application behavior.

Stage 1 is complete when ownership, consumers, states, gaps, upstream differences,
acceptance status and a gated sequence are recorded. Only this report and its
handoff may be authored. No application/configuration/skill edits, installation,
CLI generation, commits, push or publication belong to this stage.

Evidence labels used below:

- **C — code/configuration:** inspected working files; proves implementation,
  not correctness or human acceptance.
- **B — browser:** observed during this inventory; limited to the stated screen

- **H — historical:** existing decisions/task reports, including their test
  results and recorded user acceptance. These are not new executions.
- **U — upstream:** current official shadcn documentation checked online.
- **P — proposal:** a recommended future decision, not an accepted rule.

## Findings and target boundaries

The main gap is synchronization and explicit acceptance, not a missing second
library. C: local shadcn-style wrappers and Base UI already exist; four editaurus
wrappers compose them. More screens have migrated than the entry documentation
or catalog describes. Some visual rules are distributed among route CSS and
shared selectors rather than named component variants.

P: retain this dependency direction:

```text
Base UI behavior + native HTML
    ↓
src/components/ui — locally owned shadcn-compatible foundation
    ↓
src/components/editaurus + scoped visual recipes — approved Editaurus variants
    ↓
shared host compositions + src/features — data, routes, CV, filters, workflows
    ↑
catalog imports those same owners; examples have isolated synthetic state
```

Repo editaurus documentation is the target contract for this application.
Historical host documentation retains behavioral/API authority where still
applicable. The catalog demonstrates implemented states; it cannot grant design
acceptance. The portable skill receives only explicitly accepted reusable rules,
after real-screen validation and catalog alignment. It must work without this
repo, fixture IDs, recruitment transitions, routes or local vault access.

Keep the existing directories. Do not add a second `Button`, a parallel primitive
tree, a domain-aware global skill, or a separate catalog implementation. Retain
HashRouter, React/TypeScript/Vite, Zod and the existing local operations. A new
generic wrapper is justified only by a repeated gap; domain patterns remain
compositions even when shadcn offers a similarly named visual shell.

## shadcn/Base UI baseline and upstream comparison

C: `components.json` is `base-nova`, `rsc: false`, `tsx: true`, Tailwind v4
configuration with `src/app/globals.css`, neutral base color, CSS variables,
Lucide and `@/components/ui` aliases. No custom registries are configured.
`package.json` declares `@base-ui/react ^1.8.0`, `shadcn ^4.21.3` as a dev
dependency, CVA, `cn`, Tailwind 4 and `tw-animate-css`. The lock resolves Base UI
1.8.0 and shadcn 4.23.0. `globals.css` imports `shadcn/tailwind.css` and both
legacy and editaurus layers. Node used for this inventory: 24.22.3.

U: shadcn describes locally owned customizable component code. Its configuration
file guides generation; configuration alone does not establish the ancestry or
conformance of each local file. See [introduction](https://ui.shadcn.com/docs) and
[components.json](https://ui.shadcn.com/docs/components-json).

U: official component pages offer a Base UI branch. Use that branch for future
comparisons, preserving `render` where appropriate. Do not introduce Radix,
`asChild`, Command/cmdk or another form library merely to mirror an example.
The generic configuration page still illustrates `new-york`; that is not a
reason to reinitialize this existing `base-nova` project.

**Provenance precision:** the local UI wrappers have shadcn component names,
slots, CVA/composition structure and configured shadcn infrastructure. Their
Base UI imports are directly verified. An exact generated upstream revision and
per-file source hashes are not recorded, so “shadcn-style local adaptation” below
does not mean byte-identical official shadcn code. Attempts to fetch the guessed
registry JSON endpoints were unavailable; no exact registry diff is claimed.
Before replacing a primitive, record the exact upstream source revision and a
reviewable delta. No CLI `init`/`add`/overwrite was run.
